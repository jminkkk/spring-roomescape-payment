# Kafka 도입 결정 체크리스트

결제 복구 플로우를 Kafka로 전환하기 전에, **내가 직접 결정하고 근거를 쓰는** 문서.
`kafka_migration_plan/00_overview.md`의 Phase 0 표는 이 문서를 채운 뒤에 대조한다.

**규칙**
- `결정:`은 내가 쓴다. 비어 있으면 아직 안 정한 것이다.
- `근거:`가 없는 결정은 결정이 아니다. "왜 다른 선택지가 아닌가"까지 쓴다.
- 🔒 표시는 **나중에 바꾸기 어려운 항목.** 여기에 시간을 더 쓴다.
- 범위 밖이면 "범위 밖 — 이유"라고 명시한다. 빈칸과 구분된다.

---

## Part 1. 기본 결정 14개 — ✅ 작성 완료

### 1. Kafka를 왜 쓰는가

- **결정:** 복구 기록을 **실패한 자원 밖**에 두기 위해. 그리고 재시도·상한·격리를 **직접 구현하지 않기 위해.**

- **근거:**
  - 현재 구조는 PG 승인 후 DB 저장이 실패했을 때, 그 복구 기록을 **같은 DB에** 저장한다.
    그런데 저장 실패의 주 원인이 DB 장애다. 즉 **복구 기록이 가장 필요한 순간에 쓸 수 없다.**
    (`FailedPaymentRegister`의 `@Transactional(REQUIRES_NEW)`가 같은 datasource에 커넥션을 요청한다)
  - 그래서 복구 기록을 DB 밖으로 빼야 한다. 수단은 두 가지다.
    - **A. 복구 전용 별도 RDB** — 작동하지만 복구 용도로만 쓰는 DB를 상시 운영해야 하고,
      재시도 메커니즘은 **여전히 직접 만들어야 한다.**
    - **B. 이미 보유한 MQ(Kafka)** — 추가 도입 비용이 사실상 0이고, 재시도·상한·DLQ가 표준으로 딸려온다.
  - 이벤트 드리븐/MSA 구조라면 Kafka 스택이 이미 있다고 보는 것이 합리적이다. B를 채택한다.

- ⚠️ **조건부로 말할 것:** MQ가 없는 조직이라면 이걸 위해 Kafka를 도입하지 않는다.
  그 경우엔 `payment.status=IN_PROGRESS`를 쓸어가는 정산 배치가 맞다.
  목적은 특정 미들웨어가 아니라 **전용 재시도 인프라를 소유하지 않는 것**이다.

### 2. 어떤 이벤트인가 🔒

- **결정:** `PaymentPersistFailed` — **사실(fact) 기반** 네이밍.

- **근거:**
  - 사실 기반(`PaymentPersistFailed`) vs 명령 기반(`PaymentRecoveryRequested`) 중 사실을 택했다.
  - 사실 기반이면 나중에 알림·지표 등 다른 컨슈머가 붙어도 이름이 어색하지 않다.
    복구는 이 사실에 대한 **대응 정책이고, 그 정책은 컨슈머가 소유**한다.
  - 명령 기반은 의도가 명확한 대신 "무슨 일이 있었나"가 소실되고 컨슈머가 1개로 고정되는 뉘앙스가 된다.

- ⚠️ **이름에 담기지 않은 전제:** 이 이벤트의 핵심은 "PG 승인은 성공했는데 DB 저장만 실패했다"다.
  `PaymentApprovedButUnrecorded`가 더 정확하지만 길어서 택하지 않았다.
  → **PG 승인 성공이 발행 전제조건**이라는 것을 코드 주석과 Phase 6 문서에 명시한다.

### 3. Topic 🔒

- **결정:** 복구 이벤트 종류별로 **별도 토픽.** 지금은 `payment.persist.failed` 하나.

- **근거:**
  - 분류 기준은 **"컨슈머의 처리 로직이 다르면 분리"**다. 같은 "DB 저장 복구"라도 저장하는 대상이
    다르면 처리가 다르다.
  - 기술적 근거: **재시도·DLQ 정책은 리스너(=토픽) 단위로 붙는다.** 성격이 다른 이벤트를 한 토픽에
    섞으면 에러 핸들러를 공유하게 되고, 컨슈머가 타입 분기를 해야 한다.
  - 나중에 다른 복구 이벤트가 생기면 토픽을 새로 만든다. 확장 시 혼선이 없다.

- **토픽 이름:** 이벤트와 같은 **사실 기반**으로 `payment.persist.failed`. (처음엔 `payment.recovery.requested`였다)
  - 2번에서 사실 기반 이벤트를 택한 근거가 "알림·지표 컨슈머가 붙어도 자연스럽다"였다. 토픽 이름이
    복구 용도에 묶여 있으면(`recovery.requested`) 다른 컨슈머가 구독할 때 어색해져 그 근거가 무너진다.
  - 토픽 이름도 🔒다 — DLT 이름이 따라가고, 오프셋도 토픽 단위로 저장된다. 그래서 구현 전에 맞췄다.
  - 컨슈머 용도인 "복구"는 `group.id`(`roomescape-payment-recovery`, 16번)와 패키지(`payment.recovery`)에
    남긴다. **토픽은 무슨 일이 있었는지, 그룹은 누가 무엇을 하는지**를 나타낸다.

- **패키지:** 같은 원칙을 코드 위치에도 적용한다.
  - `roomescape.payment.event` — 이벤트 record(`PaymentPersistFailed`) + Publisher
  - `roomescape.payment.recovery` — 리스너 + 핸들러 + 재투입 리스너 + 컨슈머 설정
  - 처음 계획은 전부 `payment.recovery`였다. 그러면 발행하는 쪽(`PaymentService`)이 `recovery`를 import하게 되어,
    **이벤트를 발행하는 쪽이 누가 소비하는지 아는 구조**가 된다. 토픽 이름을 바꾼 것과 같은 이유로 분리했다.
  - 의존 방향은 `recovery → event`만 허용한다. `event`는 `recovery`를 모른다.
    나중에 알림 컨슈머가 붙으면 그쪽도 `event`만 의존하면 된다.

### 4. Key 🔒

- **결정:** `paymentId` (우리 애플리케이션이 관리하는 `Payment`의 PK).

- **근거:**
  - 이 이벤트의 주체는 결제다(2번 이벤트 이름과 일관).
  - **외부 시스템 키보다 우리 도메인 ID를 쓴다.** `paymentKey`는 PG가 발급한 키라 우리가 소유하지 않는다.
  - **PG가 여러 개다**(`PaymentClientType`). `paymentKey`는 해당 PG사 안에서만 유일하고 PG사 간에
    겹칠 수 있다. `paymentId`는 우리 DB PK라 전체에서 유일하다.
  - 키 선택 4가지 질문을 모두 통과한다: ① 순서 단위(불필요, 13번) ② aggregate ID(결제 → `paymentId`)
    ③ 분포(결제 1건 = 키 1개, 쏠림 없음) ④ 불변·우리 소유.
  - 멱등성 체크 단위(9번)와 일치한다 — 같은 결제에 대한 메시지는 같은 파티션으로 모인다.

- 🔴 **따라오는 작업:** ① `Payment`에 `getId()` 추가(현재 없음) ② payload에 `paymentId` 포함(→ 6번)
  — 컨슈머가 `findById`로 바로 조회할 수 있어 `findByReservation`보다 단순해진다.

- ⚠️ **지금은 키가 기능적으로 거의 무의미하다.** 파티션이 1개(5번)이고 순서 보장이 불필요(13번)하기
  때문이다. 그래도 키를 지정하는 이유는 ① 나중에 파티션을 늘릴 때 같은 키가 같은 파티션으로 모임
  ② 추적·디버깅 편의 ③ null key는 라운드로빈이라 분포를 예측할 수 없음.

### 5. Partition 🔒

- **결정:** **1개.** (replication factor 1, 로컬 범위)

- **근거:**
  - **파티션은 1 → N 증설은 가능하지만 N → 1 축소는 불가능하다.** 따라서 1개가 되돌리기 쉬운 선택이다.
  - 복구 이벤트는 **장애 시에만** 발생하므로 처리량이 극저다. 병렬성 이득이 사실상 0이다.
  - 순서 보장이 불필요하므로(13번) 파티션을 늘릴 때의 부작용(키-파티션 재배정)도 무해하다.
  - 2개로 늘리면 치르는 비용: DLQ도 파티션 수를 맞춰야 하고(`DeadLetterPublishingRecoverer`가
    원본과 같은 파티션 번호로 전송), 테스트가 복잡해진다. 얻는 것 없이 비용만 는다.
  - ❌ 기각한 근거: "파티션을 도입할 거면 의미 있게 써야 한다" — 이건 근거가 아니라 오버엔지니어링이다.

### 6. Payload 🔒

- **결정:** **`paymentId` 하나만.** `PaymentPersistFailed(Long paymentId)`

- **필드를 하나로 줄인 근거:**
  - 컨슈머 처리에는 `paymentId`만 있으면 된다. `findById`로 바로 조회한다.
  - `reservationId`(FK)와 `paymentKey`는 **`Payment` row에 이미 있다.** payload에 중복으로 실으면
    DB 값과 메시지 값이 어긋날 여지만 생긴다.
  - **되돌리기 쉬운 쪽에서 시작한다.** 21번에서 "필드는 추가만 허용"으로 정했으므로, 나중에 필드를 늘리는 건
    가능하지만 빼는 건 불가능하다. 5번(파티션 1개)과 같은 논리다.
  - 대가: DLQ 메시지를 Kafka UI로 볼 때 `paymentId`만 보인다. 예약이나 PG 키를 확인하려면 DB를 조회해야
    한다. 장애 조사 빈도가 낮아서 감수한다.

- **근거:**
  - 상태를 담으면 메시지가 **그 시점의 스냅샷**으로 굳어 낡을 위험이 있다. ID만 담으면 그 문제가 없다.
  - 컨슈머가 읽을 데이터는 **tx1에서 이미 커밋돼 있다**(예약 + `Payment(IN_PROGRESS)`). 재조회가 가능하다.
  - 기존 방식(역직렬화한 `Reservation`/`Payment` 엔티티를 그대로 `save()`)은 전체 스냅샷을 덮어써서
    위험했다.

### 7. Serialization 🔒

- **결정:** **JSON** (`JsonSerializer`/`JsonDeserializer`).

- **근거:**
  - Producer와 Consumer가 **같은 애플리케이션**이다. Schema Registry의 이득(언어 간 호환, 중앙 스키마
    관리)이 발생하지 않는다.
  - Avro/Protobuf를 택할 이유가 없다. 스키마 파일·빌드 플러그인·레지스트리 운영 비용만 는다.
  - 나중에 외부 서비스가 이 토픽을 구독하게 되면 재검토한다(→ 21번 스키마 진화).

### 8. Delivery

- **결정:** **at-least-once.** (Kafka/Spring Kafka 기본 설정)

- **근거:**
  - **선택지가 사실상 하나다.** exactly-once(Kafka 트랜잭션)는 **Kafka에서 읽어 Kafka로 쓸 때만**
    성립한다. 우리 컨슈머는 **외부 DB**에 쓰므로 Kafka EOS로 보장되지 않는다.
  - at-most-once는 유실을 허용하는데, 돈이 걸린 플로우라 불가능하다.
  - 따라서 `at-least-once + 컨슈머 멱등성`(9번)이 유일한 조합이다.

### 9. Consumer 멱등성

- **결정:** **① 처리 전 상태 확인.** Payment가 이미 `COMPLETED`면 skip.

- **근거:**
  - 도메인에 이미 "처리됐음"을 알려주는 상태 컬럼(`Payment.status`)이 있다. 가장 싼 방법이다.
  - dedup 테이블(②)은 별도 저장소와 정리 로직이 필요하고, DB 유니크 제약(③)은 이 플로우가
    insert가 아니라 update라 적용되지 않는다.
  - DLQ 재투입(12번)도 중복 전달이므로 멱등성은 선택이 아니라 필수다.

- 🔴 **구현 전 선행 작업:** `Payment`에 상태를 읽을 방법이 없다. getter는 `getPaymentKey`/`getOrderId`/
  `getAmount`뿐이고 `getStatus()`가 없다. → **`Payment.isCompleted()` 도메인 메서드를 추가**한다
  (getter 노출보다 캡슐화 유지). TDD 첫 단계는 `PaymentTest`가 된다.

### 10. Offset

- **결정:** **처리 후 커밋** (Spring Kafka 기본값 유지).

- **근거:**
  - 처리 **전** 커밋하면 처리 중 장애 시 메시지가 유실된다. 돈이 걸려서 허용 불가.
  - 처리 **후** 커밋하면 커밋 전 장애 시 중복 수신이 발생하지만, 9번에서 멱등성을 보장했으므로 무해하다.
  - 8·9·10은 한 덩어리다: at-least-once → 중복 발생 → 멱등성으로 흡수 → 그래서 처리 후 커밋이 안전.

### 11. Retry

- **결정:** **3회** (`DefaultErrorHandler` + `FixedBackOff`). 역할은 **"일시적 블립 흡수"로 한정.**
  재시도로 복구 불가능한 예외는 즉시 DLQ로 보낸다.

- **근거:**
  - **재시도 가능 (3회가 담당)** — DB 커넥션 블립, 타임아웃, 커넥션 풀 고갈, 락 경합
  - **재시도 불가 (즉시 DLQ 대상)**
    1. 🔴 **역직렬화 실패** — payload 깨짐/스키마 변경. 가장 흔한 poison pill (→ 23번)
    2. **Payment 미존재** — tx1이 커밋됐으면 반드시 있어야 한다. 없다는 건 정합성 이상이고 재시도해도
       안 생긴다
    3. **코드 버그(NPE 등)**
    4. 제약 위반 — 이 플로우는 update라 가능성은 낮다
  - **DB 장애(주 실패 모드)는 3회로 복구되지 않는다.** 수 분~수십 분 지속되는데 3회는 수 초에
    소진된다. 그건 DLQ가 받는다(12번). 재시도 횟수를 늘려도 의미가 없고, 블로킹 재시도라 늘리면
    파티션이 정체된다.

### 12. DLQ

- **결정:** 재시도 3회로 복구되지 않은 **모든 예외**가 DLQ로 간다. 재처리는 `autoStartup = "false"`
  리스너를 **운영자가 수동으로 켜서** 하고, 원본 토픽으로 되돌리지 않고 **같은 핸들러로 직접 처리**한다.

- **근거:**
  - **DB 복구 시점을 시스템이 판단할 수 없다.** 커넥션은 되지만 느리거나 간헐 실패하는 "반쯤 살아난"
    상태에서 자동 재시도가 계속 돌면, 회복 중인 DB에 **재시도 폭풍**을 얹는다.
  - **자동화가 많다고 좋은 것이 아니다 (DDIA).** 이미 대응 로직이 여러 겹(보상 취소 → 복구 이벤트 →
    재시도 → DLQ)인데 DLQ까지 자동화하면 대응 경로가 과도해져 **처리가 복잡해지고 문제를 놓치게 된다.**
    전체를 자동화하면 오히려 전체를 신뢰할 수 없다.
  - **poison pill 위험.** 자동 재투입은 영구 실패 메시지가 DLQ ↔ 원본 토픽을 무한 왕복하게 만든다.
    왕복 횟수를 헤더에 누적하는 로직을 또 만들어야 한다.
  - **리스너 방식을 택한 이유(스크립트 대신):** ① TDD가 필수인데 셸 스크립트는 테스트를 쓸 수 없고
    리스너는 `@EmbeddedKafka`로 검증 가능하다 ② Actuator가 이미 있어 토글 수단이 있다
    ③ 원본 컨슈머의 핸들러를 재사용하므로 로직 중복이 없다.
  - **원본 토픽으로 되돌리지 않는 이유:** 왕복하면 횟수 카운트 로직이 필요해진다. 직접 처리하면
    그게 불필요하고, 또 실패하면 메시지가 DLT에 그대로 남아 사람이 다시 보게 된다.
  - 멱등성(9번)이 보장돼 있어 재투입 중복은 무해하다.

- **조사 수단:** `DeadLetterPublishingRecoverer`가 헤더에 원인을 같이 넣는다 —
  `kafka_dlt-original-topic`, `-original-partition`, `-original-offset`, `-exception-fqcn`,
  `-exception-message`, `-exception-stacktrace`. Kafka UI에서 DLT 메시지를 열면 실패 원인이 바로 보인다.

### 13. Ordering

- **결정:** **순서 보장 불필요.**

- **근거:**
  - 동기화가 중요한 것은 예약(좌석 선점)인데, 그건 **앞선 tx1에서 이미 선점**이 끝났다.
  - Payment는 reservation과 1:1이고, 복구 이벤트는 키당 실질적으로 1건이다. 순서를 따질 메시지가 둘 이상
    생기지 않는다.
  - 카프카는 파티션 내에서만 순서를 보장하는데, 애초에 순서가 필요 없으므로 이 제약이 영향을 주지 않는다.
  - → 이것이 5번(파티션 1개)과 4번(키의 기능적 무의미)의 근거가 된다.

### 14. Lag

- **결정:** lag 임계값은 **건수가 아니라 시간 기준** — "1건 이상이 5분 넘게 유지되면 장애".
  단, 이 토픽에서 더 중요한 지표는 아래 ①②다.

- **근거:**
  - 이 토픽은 **평시 메시지가 0건**이다(장애 시에만 발생). 일반 토픽처럼 "100건 쌓이면 알림"은
    의미가 없다.
  - 실제로 봐야 할 지표 3개:
    1. **`.DLT` 적재 건수** — 0이 아니면 즉시 알림 (= 수동 개입 필요, 12번)
    2. **원본 토픽 발행 건수** — 장애 발생 횟수 그 자체
    3. **consumer lag** — 컨슈머가 살아 있는지 확인용
  - `management.endpoints`에 prometheus가 이미 노출돼 있어 연결 가능하다. 실제 알림 연동은 범위 밖.

## Part 2. Part 1에 없지만 Phase 2 시작 전에 반드시 필요한 것 — ✅ 작성 완료

Part 1을 다 채워도 구현을 시작하면 바로 막히는 항목들. 위험한 순서로 정렬했다.

### 15. `auto.offset.reset` 🔴 가장 위험

컨슈머 그룹이 **처음 뜰 때**(또는 커밋된 오프셋이 retention으로 삭제됐을 때) 어디서부터 읽는가.

- **결정:** **`earliest`**

- **근거:**
  - 기본값 `latest`는 컨슈머 그룹이 처음 뜨거나 `group.id`가 바뀌었을 때, **그 전에 쌓인 복구 메시지를
    건너뛴다.** 복구 플로우에서 이는 결제 유실이다.
  - `earliest`의 부작용은 이미 처리한 메시지를 다시 읽는 중복인데, 9번 멱등성(`Payment` 상태가
    `COMPLETED`면 skip)이 흡수한다.
  - 10번 Offset과 같은 구조의 판단이다: **유실은 허용 불가, 중복은 멱등성으로 흡수.**
  - TDD에서도 필요하다 — `latest`면 `@EmbeddedKafka` 테스트에서 컨슈머가 구독을 마치기 전에 보낸
    메시지를 놓쳐 테스트가 간헐적으로 실패한다.

### 16. Consumer group id

group.id를 무엇으로 할 것인가.

- **결정:** 메인 리스너 `roomescape-payment-recovery`, DLQ 재투입 리스너 `roomescape-payment-recovery-dlt-replay`로 **분리**.

- **근거:**
  - 두 리스너는 생명주기가 다르다. 메인은 항상 켜져 있고, 재투입 리스너는 평시 꺼져 있다가 운영자가 켠다(12번).
  - 그룹이 나뉘면 lag도 그룹별로 보여서 재투입 진행 상황을 따로 추적할 수 있다.
  - 오프셋은 (group, topic, partition) 단위로 저장되고 두 리스너는 토픽이 다르므로, 같은 그룹이어도
    기술적 충돌은 없다. 그래도 모니터링에서 섞여 보이므로 분리한다.
  - ⚠️ `group.id`를 바꾸면 오프셋이 초기화되어 15번(`earliest`)이 발동한다. 운영 중에는 이름을 바꾸지 않는다.

### 17. 토픽 retention / cleanup.policy

원본 토픽과 DLQ 토픽 각각.

- **결정 (원본):** `cleanup.policy=delete`, retention 기본값 7일
- **결정 (DLQ):** `cleanup.policy=delete`, retention **30일** (명시)

- **근거:**
  - 이 토픽의 메시지는 "상태"가 아니라 **"한 번 처리하면 끝나는 작업"**이다. 처리가 끝나면 버려도 된다
    → `delete`.
  - ❌ `compact` 기각: 키별 최신 1건을 **영구 보존**하는 방식이다. 결제 1건 = 메시지 1건이라 남길 "최신"이
    따로 없고, 이미 처리한 메시지가 영원히 쌓인다. 15번(`earliest`)과 겹치면 새 그룹이 뜰 때마다 전부
    다시 읽는다(멱등성 덕분에 결과는 안전하지만 쓸데없는 작업이다).
  - 원본은 컨슈머가 몇 초 안에 처리하므로 7일이면 충분하다.
  - DLQ는 **사람을 기다리는 곳**이다(12번 수동 재처리). 연휴가 끼면 7일은 모자랄 수 있다.
  - 복구 이력을 감사 목적으로 남기는 것은 Kafka의 역할이 아니다. 필요하면 로그나 DB가 맡는다.
  - 참고: 삭제는 메시지 단위가 아니라 세그먼트(파일 조각) 단위라 정확히 기한에 맞춰 지워지지는 않는다.

### 18. Producer 멱등성 (`enable.idempotence`)

- **결정:** `enable.idempotence=true`, `acks=all`을 **명시**한다.

- **근거:**
  - 8~10번은 컨슈머 쪽 중복이었다. 이건 **Producer → 브로커 구간** 중복이다. ack 응답이 유실되면
    Producer는 실패한 줄 알고 재전송하고, 브로커에 같은 메시지가 2건 쌓인다.
  - 동작: Producer가 배치마다 (Producer ID, 시퀀스 번호)를 붙이고, 브로커가 Producer별·파티션별로
    최근 5개 배치의 시퀀스를 기억해 같은 번호를 버린다. (`max.in.flight.requests.per.connection ≤ 5` 제약의 이유)
    이 값들은 앱이 다루는 record header가 아니라 프로토콜 레벨의 **batch header**에 들어간다
    (RDB로 치면 InnoDB 숨김 컬럼 `DB_TRX_ID` 같은 엔진 전용 메타 정보).
  - Kafka 3.0+ 클라이언트는 기본값이 true일 가능성이 높지만, **명시해서 의도를 코드에 남긴다.**
    다른 설정과 충돌할 때 조용히 꺼지는지 에러가 나는지는 버전마다 달라 확인이 필요하다.

- ⚠️ **한계:** 앱을 재시작하면 Producer ID가 새로 발급된다. 그래서 **같은 세션 안의 재전송**만 막는다.
  재시작을 넘는 중복까지 막으려면 `transactional.id`가 필요하지만, 컨슈머 멱등성(9번)이 최종 방어선이므로
  도입하지 않는다.

### 19. Consumer concurrency

- **결정:** concurrency **1**. `max.poll.interval.ms`는 기본값(5분) 유지.

- **근거:**
  - 파티션 하나는 그룹 안에서 컨슈머 하나만 처리할 수 있다. 파티션이 1개(5번)이므로 동시 처리 상한도 1이다.
    2 이상으로 올려도 나머지 스레드는 논다.
  - 운영에서 인스턴스를 여러 대 띄우면 1대만 소비하고 나머지는 대기한다. 처리량이 극저인 이 토픽에서는
    오히려 장점이다 — 소비 중인 인스턴스가 죽으면 리밸런싱으로 대기 인스턴스가 이어받는 **자동 장애 조치**가 된다.
  - 재시도가 3회로 짧아(11번) 처리 시간이 5분을 넘을 일이 없다.
  - 참고: 나중에 concurrency를 올릴 때는 **DB 커넥션 풀**을 같이 봐야 한다. 컨슈머 스레드도 처리 중에
    HikariCP 커넥션을 쓰므로 웹 요청과 경쟁한다.

### 20. 토픽 생성 주체

수동 CLI / auto-create / 애플리케이션 선언(`NewTopic` 빈) / IaC.

- **결정:** `@Bean NewTopic`으로 원본·DLT **둘 다 선언**(파티션 1, replicas 1, DLT retention 30일).
  로컬 브로커는 **auto-create를 끈다.**

- **근거:**
  - 파티션 수와 retention이 코드에 남아 재현된다. TDD 테스트 환경에서도 같은 토픽 구성이 보장된다.
  - DLT 파티션 수를 원본과 맞출 수 있다. `DeadLetterPublishingRecoverer`는 원본과 같은 파티션 번호로
    보내므로, 다르면 전송이 실패한다(5번).
  - auto-create를 끄면 토픽명 오타 시 조용히 새 토픽이 생기지 않고 바로 에러가 난다.
  - ❌ 수동 CLI 기각: 환경마다 다시 해야 하고 재현되지 않는다.
  - ❌ auto-create 기각: 파티션 수를 브로커 기본값에 맡기게 된다.
  - 운영에서는 IaC나 플랫폼팀이 토픽을 만드는 경우가 많다. 이번 범위(로컬) 밖이다.

### 21. 스키마 진화

payload에 필드를 추가/삭제할 때의 호환성 정책.

- **결정:**
  - 필드는 **추가만 허용**한다. 삭제·이름 변경은 금지하고, 필요하면 새 이벤트(새 토픽)로 만든다.
  - **타입 헤더를 끄고 컨슈머에 기본 타입을 지정**한다.
    (`spring.json.add.type.headers=false`, `spring.json.value.default.type=...PaymentPersistFailed`)

- **근거:**
  - Producer와 Consumer가 같은 앱이라 같이 배포되지만, **DLQ에는 최대 30일 전 형식의 메시지가 남아 있다**(17번).
    따라서 새 코드가 옛 메시지를 읽을 수 있어야 한다(backward 호환).
  - 🔴 Spring Kafka `JsonSerializer`는 기본적으로 record header(`__TypeId__`)에 **클래스 전체 이름**을 넣고,
    컨슈머는 그 이름으로 역직렬화할 클래스를 찾는다. 이번 전환에서는 이벤트 이름(`PaymentPersistFailed`)과
    패키지(`payment.event`, 3번)가 바뀌므로, 타입 헤더를 쓰면 이름이나 위치를 옮기는 순간 옛 메시지를 읽지 못한다.
  - 같은 앱 안의 단일 이벤트 토픽이라 타입 정보를 헤더로 실어 나를 필요가 없다.

- ⚠️ **확인 필요:** 모르는 필드가 들어왔을 때 무시하는지. Spring Kafka 기본 ObjectMapper는 무시하는 것으로
  알고 있지만 버전별로 확인한다.

### 22. 보안 (SASL / TLS / ACL)

- **결정:** **범위 밖** — 이번 전환은 로컬(docker-compose) 범위다.

- **운영에서 필요한 것:**
  - 인증: SASL/SCRAM
  - 암호화: TLS
  - 인가: ACL로 `payment.persist.failed` **쓰기 권한을 결제 서비스에만** 준다.
    아무 서비스나 `PaymentPersistFailed`를 발행할 수 있으면 컨슈머가 그 메시지로 결제를 `COMPLETED` 처리한다.

### 23. 역직렬화 실패 처리 🔴 (11번에서 파생)

`ErrorHandlingDeserializer`를 쓸 것인가.

- **결정:** `ErrorHandlingDeserializer`로 `JsonDeserializer`를 **감싼다.**

- **근거:**
  - 역직렬화는 리스너 메서드에 도달하기 **전**, `poll()` 단계에서 일어난다. 여기서 예외가 나면
    `DefaultErrorHandler`가 정상적으로 처리하지 못하고 같은 메시지에서 계속 실패할 수 있다.
  - `ErrorHandlingDeserializer`는 실패 시 예외를 던지는 대신 value를 null로 두고 예외 정보를 헤더에 담아
    넘긴다. 그러면 리스너 단계에서 `DefaultErrorHandler`가 `DeserializationException`으로 인식하고,
    이를 **기본적으로 재시도 불가 예외로 분류**해 바로 DLT로 보낸다.
  - 11번의 "역직렬화 실패는 즉시 DLQ"를 설정만으로 달성한다.

- **함께 할 것:** 11번의 "Payment 미존재"도 커스텀 예외로 만들어 `addNotRetryableExceptions`에 등록한다.
  재시도해도 생기지 않는 데이터를 3회 기다릴 이유가 없다.

### 24. 배치 단위 — 컨슈머를 어디서 실행하는가 🔒

별도 애플리케이션 / 별도 모듈 / 같은 앱을 역할별로 배포 / 같은 앱.

- **결정:** **같은 애플리케이션.** `payment.event` / `payment.recovery` 패키지로만 나눈다 (3번).

- **근거:**
  - **분리해도 주 실패 모드에 도움이 안 된다.** 컨슈머는 `Payment`를 `COMPLETED`로 바꿔야 하므로 같은 DB가
    필요하다. DB 장애 시 다른 인스턴스로 옮긴 컨슈머도 같이 실패한다. 이 장애를 버티는 장치는 DLQ와
    재투입(12번)이지 컨슈머 위치가 아니다.
  - **앱이 죽는 경우는 Kafka가 이미 해결한다.** 메시지는 Kafka에 남아 재시작 후 이어서 읽히고, 인스턴스가
    여러 대면 리밸런싱으로 다른 인스턴스가 넘겨받는다(19번). Kafka가 시간적 분리를 해주므로 공간적 분리
    (다른 인스턴스)까지 필요하지 않다.
  - ❌ **별도 애플리케이션 기각 — 데이터 소유권 위반.** 별도 복구 서비스가 `payment` 테이블에 직접 쓰면
    두 서비스가 같은 테이블을 수정하게 된다. 결제 서비스 API를 호출하게 만들면 그 API가 장애 중인 같은 DB에
    의존한다. **복구 컨슈머는 `Payment`를 소유한 서비스 안에 있어야 한다.**
  - ❌ **별도 모듈 기각 — 장애 격리 수단이 아니다.** 모듈은 "어떤 코드가 어떤 코드를 import할 수 있는가"를
    강제하는 컴파일 타임 도구다. 같은 jar로 묶여 같은 프로세스에서 돈다. 의존 방향은 패키지 규칙으로 충분하다.

- 🟡 **다시 검토할 시점 — 같은 앱을 api / worker 역할로 나눠 배포:** 코드는 하나로 두고 인스턴스마다 역할만
  다르게 띄운다(api 인스턴스는 `spring.kafka.listener.auto-startup=false`). 아래 신호가 보이면 검토한다.
  - 컨슈머 처리량이 커져 웹 요청과 **DB 커넥션 풀을 두고 경쟁**할 때
  - 컨슈머 버그(메모리 누수 등)가 API까지 죽이는 것을 막아야 할 때
  - 지금은 장애 시에만 메시지가 들어오고 concurrency도 1이라 해당 없다.

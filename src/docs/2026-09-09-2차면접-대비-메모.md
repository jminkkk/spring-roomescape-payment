> 2026-09-09 작성. 모의면접 중 발견한 것 위주. 답을 확정하지 못한 것만 모은다.

## 1. PG 콜 "중"의 복구가 없다 + 증거까지 삭제된다 ⚠️

### 현재 코드

```java
// ReservationApplicationService.java:27-32
try {
    paymentService.callPG(ConfirmPaymentRequest.from(request));
} catch (Exception e) {
    reservationService.cancelReservation(reservation.getId());  // ← Payment + Reservation 삭제
    throw e;
}
```

`cancelReservation`은 `Payment`(IN_PROGRESS)와 `Reservation`을 **삭제**한다.
리드 타임아웃도 `Exception`이므로 이 경로를 탄다.

### 복구 커버리지

| 구간 | 복구 |
|---|---|
| PG 콜 성공 → DB 저장(TX2) 실패 | ✅ 롤백 감지 → `outbox_event` → `OutboxProcessor`(60초) |
| **PG 콜 중 타임아웃 / 예외** | ❌ 없음. 게다가 기록까지 삭제 |

**PG 승인 여부가 가장 불확실한 구간이 무방비이고, 복구에 필요한 `paymentKey`·`orderId`·금액이 담긴 행을 지운다.**

### 고민할 것

- 보상(삭제)을 **에러 유형별로 갈라야 한다**
  - `FAILED_FINAL`(잔액부족 등, PG 미승인 확실) → 삭제 OK
  - `UNKNOWN`(리드 타임아웃, 5xx) → **삭제하면 안 됨.** 상태만 전이시키고 남겨야 함
- 삭제 대신 상태 전이로 바꾸면 `Payment`가 이력으로 남는데, 그때 `Reservation` 슬롯 점유는 어떻게 할 것인가?
  - **결론: 잡고 있는다.** 트레이드오프가 아니라 비대칭이다.

    | 오판 | 결과 |
    |---|---|
    | 잡고 있었는데 실제로는 결제 실패 | 몇 분간 슬롯 미판매. **복구 가능** |
    | 놔줬는데 실제로는 결제 성공 | 남이 예약 → 돈 받은 예약에 자리 없음. **복구 불가** |

  - 되돌릴 수 없는 쪽을 피한다.
- 불명 상태를 끝내는 방법: 조회를 N회 시도하고도 불명이면 **취소 요청을 보내 상태를 강제 확정**한다.
  - 미승인 → 취소가 에러 → "결제 안 됨" 확정
  - 승인 → 취소 성공 → 환불 후 슬롯 해제
  - 주의: 실제 승인 건을 취소하면 그 사용자는 예약을 잃는다. 이미 "확인 중"으로 안내한 상태라 일관되지만, 고아 결제와 비교해 정책 판단이 필요하다.

## 2. `FAILED_UNKNOWN` 상태를 누가 기록하는가

응답을 받아야 기록할 수 있는데, 응답을 못 받는 상황이 바로 `UNKNOWN`이다.
기록 시도 전에 프로세스가 죽으면 아무것도 안 남는다.

→ 그래서 스케줄러는 `UNKNOWN`만 볼 게 아니라 **`IN_PROGRESS`로 N분 이상 머문 건**도 같이 긁어야 한다.
`IN_PROGRESS`는 PG 호출 *전에* 커밋되므로 크래시와 무관하게 남는다.

### 고민할 것
- N분을 얼마로 잡을 것인가 (`responseTimeout`이 현재 1분)
- 스케줄러가 주기적으로 도는가, 서버 기동 시에만 도는가

## 3. 대사(reconciliation)를 어떻게 할 것인가

- PG 조회 API(`GET /v1/payments/{paymentKey}`)로 물어볼 것인가
- 아니면 같은 `paymentKey`로 confirm을 재호출해서 `ALREADY_PROCESSED_PAYMENT`로 판별할 것인가
- 후자는 조회 API 없이 되지만, **실제 승인 금액을 확인할 수 없다** (금액 위변조 검증 불가)

### 고민할 것
- 동기(사용자 요청 안) vs 배치 — 즉시성 때문에 배치로 결론냈으나, 배치 주기와 사용자 안내 문구를 정해야 함
- 사용자에게 "실패"가 아니라 **"확인 중"**으로 응답해야 새 `paymentKey` 발급을 막는다 → 프론트가 같은 `paymentKey`로 재시도하는 게 전제

## 4. 다중 인스턴스에서 스케줄러 중복 실행

`@Scheduled`는 인스턴스마다 독립 실행된다. N대면 같은 건을 N번 집는다.

- `SELECT ... FOR UPDATE SKIP LOCKED`로 클레임
- ShedLock 등 분산 락으로 단일 인스턴스만 실행
- 상태 전이를 CAS로 (`UPDATE ... WHERE id=? AND status='PENDING'`, 영향 행 1이면 획득)

### 고민할 것
- 이 규모에서 어느 쪽이 맞는지 근거를 정해야 함

## 5. 결제 금액 검증이 없다 ⚠️ (핀테크 면접에서 최우선)

`Theme`에 **가격 필드가 없다.** (`id`, `name`, `description`, `thumbnail`이 전부)

결제 금액의 유일한 출처는 `CreateMyReservationRequest.amount` — **클라이언트가 보낸 값**이고, 검증 없이 그대로 PG로 나간다.
→ `{"themeId": 1, "amount": 100}`이면 100원에 예약된다.

그리고 이게 대사 설계 전체를 무력화한다. "우리 쪽 금액과 PG 승인 금액 대조"에서 **우리 쪽 금액 = 사용자가 보낸 금액**이라 항상 일치한다.

### 고민할 것
- `Theme`에 가격을 넣고 `themeId`로 서버가 조회 → 클라이언트 금액과 불일치 시 PG 호출 전 거절
- 모의면접에서 "가격 필드 있나요?"에 **"네"라고 단정**했다. 확인하면 바로 드러나는 사실이므로 주의.

## 7. 재시도 전략 — 설명과 구현이 어긋난다

모의면접에서 *"토스 에러 응답을 재시도 가능/불가로 분류한 후 retry 전략을 커스텀"*이라고 설명했으나, 실제 `IdempotencyKeyRetryStrategy`는:

```java
retriableCodes = { 429, 503 }                    // HTTP 상태 코드로만 판단
nonRetriableIOExceptionClasses = { InterruptedIOException, ConnectException, ... }
handleAsIdempotent() → 멱등 메서드 or Idempotency-Key 헤더 존재 시 재시도
maxRetries = 1
```

- **`TossErrorCode`를 참조하지 않는다.** 토스 에러코드 분류는 `TossPaymentErrorHandler` 쪽에 따로 있고 재시도 전략과 연결돼 있지 않다.
- **커넥션 타임아웃은 재시도 가능**하다고 말했으나 `ConnectException`이 non-retriable 목록에 있다.
- 리드 타임아웃(`SocketTimeoutException` → `InterruptedIOException`)이 재시도 안 되는 것은 설명과 일치.

### 진짜 설명 포인트 (놓쳤던 것)
`handleAsIdempotent()` — **"멱등키가 붙어 있으면 재시도해도 안전하다"**는 판단이 이 클래스의 핵심이고 이름의 이유다.

# 대기(Waiting) 기능 스펙

## 핵심 개념

- **대기(Waiting):** 이미 예약이 찬 슬롯(날짜 + 시간 + 테마)에 대해 순번을 등록하는 것
- **승격:** 예약 취소 시, 가장 먼저 등록된 대기자가 자동으로 해당 예약의 예약자가 되는 것

---

## Functional Requirements

### FR-1. 대기 생성
- 사용자는 이미 예약이 존재하는 슬롯에 대기를 등록할 수 있다.
- 대기 등록 시 순위(몇 번째 대기인지)를 응답으로 받는다.

### FR-2. 대기 취소
- 사용자는 본인의 대기를 취소할 수 있다.

### FR-3. 대기 거절 (관리자)
- 관리자는 임의의 대기를 거절(삭제)할 수 있다.

### FR-4. 내 대기 목록 조회
- 사용자는 본인의 대기 목록을 순위와 함께 조회할 수 있다.

### FR-5. 전체 대기 목록 조회 (관리자)
- 관리자는 전체 대기 목록을 조회할 수 있다.

### FR-6. 대기 -> 예약 승격
- 예약이 취소되면, 해당 슬롯의 1순위 대기자가 자동으로 예약자로 승격된다.
- 승격된 예약은 PENDING 상태가 되며, 사용자가 결제를 완료하면 CONFIRMED로 전환된다.
- 승격된 대기 레코드는 삭제된다.

### FR-7. 승격 알림
- 대기자가 예약으로 승격되면, 해당 사용자에게 이메일 알림을 발송한다.
- 알림 발송 실패 시 Outbox 패턴으로 재시도한다 (기존 notification 인프라 활용).

---

## Acceptance Criteria

### AC-1. 대기 생성
- [x] 예약이 존재하는 슬롯에 대기 요청 -> 201 Created, 대기 ID 반환
- [ ] 예약이 없는 슬롯에 대기 요청 -> 400 Bad Request
- [ ] 같은 회원이 같은 예약에 중복 대기 요청 -> 400 Bad Request
- [ ] 해당 예약의 예약자 본인이 대기 요청 -> 400 Bad Request

### AC-2. 대기 취소
- [x] 본인 대기 삭제 요청 -> 204 No Content
- [x] 타인 대기 삭제 요청 -> 403 Forbidden
- [x] 존재하지 않는 대기 삭제 요청 -> 404 Not Found

### AC-3. 대기 거절 (관리자)
- [ ] 관리자가 임의 대기 거절 -> 204 No Content (본인 소유 여부 무관)
- [x] 존재하지 않는 대기 거절 -> 404 Not Found

### AC-4. 내 대기 목록 조회
- [x] 본인 대기 목록 + 각 대기의 순위가 포함되어 반환

### AC-5. 대기 -> 예약 승격
- [x] 예약 취소 시 대기 존재 -> 1순위 대기자가 예약자로 교체됨
- [ ] 승격된 예약이 PENDING 상태가 됨
- [x] 승격된 대기 레코드가 삭제됨
- [x] 대기가 없는 예약 취소 -> 예약만 삭제됨

### AC-6. 승격 알림
- [ ] 승격 시 해당 사용자에게 이메일 알림 발송
- [ ] 알림 발송 실패 시 Outbox에 실패 이벤트 저장

> `[x]` = 현재 구현됨, `[ ]` = 구현 필요

---

## Edge Cases

| # | 시나리오 | 기대 동작 |
|---|---------|----------|
| E-1 | 동시에 같은 회원이 같은 예약에 대기 2건 요청 | 1건만 성공, 나머지 400 (DB unique 제약) |
| E-2 | 대기 승격 중 다른 요청이 같은 대기를 참조 | 트랜잭션으로 격리, 중복 승격 방지 |
| E-3 | 예약자가 취소하고, 대기자가 승격된 직후 또 취소 발생 | 다음 순위 대기자가 다시 승격 |
| E-4 | 대기가 1건인 상태에서 대기 취소와 예약 취소가 동시 발생 | 대기가 이미 삭제됐으면 예약만 삭제 |
| E-5 | 승격 대상 대기자가 이미 탈퇴한 회원 | 현재 스펙 외 — 회원 탈퇴 시 대기 정리 필요 |
| E-6 | 과거 날짜 슬롯에 대기 등록 시도 | 예약 자체가 과거 날짜를 막으므로, 예약이 존재하면 대기는 허용 (별도 검증 불필요) |
| E-7 | 승격 알림 발송 실패 | Outbox에 실패 이벤트 저장, 승격 자체는 롤백하지 않음 (알림은 best-effort) |

## Non-functional Requirements

| # | 항목 | 요구사항 |
|---|------|---------|
| NFR-1 | 데이터 정합성 | 대기 생성/삭제/승격은 트랜잭션 내에서 원자적으로 실행 |
| NFR-2 | 중복 방지 | (member_id, reservation_id) DB unique 제약조건으로 애플리케이션 레벨 race condition 방어 |
| NFR-3 | 순서 보장 | 대기 순서는 ID 오름차순(= 등록 시간순)으로 결정, 쿼리에 ORDER BY 명시 |
| NFR-4 | 권한 분리 | 사용자 취소와 관리자 거절은 별도 메서드로 권한 체크 분리 |

---

## Out of Scope

- 대기 만료 (일정 시간 내 결제 미완료 시 자동 취소)
- 대기 최대 인원 제한
- 회원 탈퇴 시 대기 정리
- 대기 순서 변경 (관리자가 수동으로 순서 조정)

---

## 현재 구현 대비 변경 필요 사항

| # | 항목 | 현재 | 변경 |
|---|------|------|------|
| 1 | WaitingService 트랜잭션 | 없음 | `@Transactional` 추가 |
| 2 | 대기 순서 보장 | `findFirstByReservation` (정렬 미지정) | `findFirstByReservationOrderByIdAsc` |
| 3 | 예약자 본인 대기 방지 | 검증 없음 | 대기 생성 시 예약자 본인 여부 검증 추가 |
| 4 | Admin 거절 권한 | `deleteWaiting` 공용 (본인 체크) | 관리자용 거절 메서드 분리 |
| 5 | 승격 시 예약 상태 | member만 교체, 상태 변경 없음 | 승격 시 예약을 PENDING 상태로 전환 |
| 6 | 중복 대기 방지 | 애플리케이션 레벨 체크만 | DB unique 제약조건 추가 |
| 7 | 승격 알림 | 없음 | 승격 시 이메일 알림 발송 (Outbox 패턴, 기존 notification 인프라 활용) |

기존 문서들의 스타일(문제 제기 → 코드로 구조 설명 → 결정 근거)을 참고.

## 할 일

1. `src/docs/technical_decision/11_outbox-to-kafka-dlq.md` 작성
   (번호는 작성 시점에 `ls src/docs/technical_decision/`로 재확인 — 현재 최신이 10번).

   **반드시 포함할 내용 — 아래 논증 순서를 지킬 것.** 이 순서가 깨지면 "왜 Kafka인가"가 유행처럼
   읽힌다:

   ① **실패 모드를 먼저 특정한다.** tx3(`completePayment`) 롤백의 주 원인은 DB 장애이고, 지속 시간은
      수 분~수십 분이다. 이게 모든 정책의 출발점이다.

   ② **기존 Outbox의 구조적 결함.** `@Transactional(REQUIRES_NEW)`로 **같은 datasource에** 복구
      레코드를 쓰려 했기 때문에, DB 장애에서 tx4도 함께 실패한다. 게다가 `afterCompletion`에서 던진
      예외는 Spring이 삼키므로 **무음 유실**이다 — 돈은 빠져나갔는데 흔적이 없다.
      - 여기서 짚을 핵심: Transactional Outbox는 원래 "업무 커밋 성공 + 메시지 발행 실패"를 막는
        패턴이라 **DB가 살아 있음을 전제**한다. 우리 실패 모드는 전제가 맞지 않았다.
      - 설정 실수가 아니라 패턴 적용 자체가 어긋났다는 점을 분명히.

   ③ **재시도 인프라를 자가 구현한 비용.** `OutboxProcessor`는 `@EnableScheduling`이 없어서
      **단 한 번도 실행되지 않았고**, 아무도 몰랐다. 설령 돌았어도 `PENDING`만 조회해서 1회 실패 시
      영구 방치였다. 상태 머신 + 폴링 + retryCount 상한 + 가시성을 직접 소유하면 이렇게 조용히 죽는다.

   ④ **②가 요구하는 결론: 복구 기록은 실패한 자원 밖에 있어야 한다.** 그 수단 두 개를 비교한다.
      - **A. 복구 전용 별도 DB(별도 datasource)** — 작동한다. 하지만 복구 용도로만 쓰는 DB를 상시
        운영해야 하고, ③의 재시도 인프라는 **여전히 직접 만들어야 한다.**
      - **B. 이미 보유한 MQ(Kafka)에 위임** — 추가 도입 비용이 사실상 0이고(이벤트 드리븐 조직은
        이미 MQ를 운영한다), 재시도·상한·DLQ가 표준으로 딸려온다.
      - 🔴 **A를 "검토 후 기각한 대안"으로 반드시 명시할 것.** 기각된 대안이 적힌 문서가 신뢰받는다.
        B가 ②와 ③을 **한 번에** 해결한다는 것이 채택 근거다.
      - 정직하게 쓸 것: MQ가 없는 조직이라면 이걸 위해 Kafka를 도입하지는 않는다. 그 경우엔
        `IN_PROGRESS` 정산 배치 쪽이 합리적이다. 목적은 특정 미들웨어가 아니라 **전용 재시도 인프라를
        소유하지 않는 것**이다.

   ⑤ **DLQ의 위치를 솔직하게 쓴다.** Consumer 재시도 3회는 일시적 블립만 흡수하고, DB 장애는
      버티지 못한다(Consumer도 같은 DB를 재조회한다). 따라서 **DLQ는 드문 예외 창구가 아니라
      지속 장애 건의 정상 착지점**이고, 재투입 절차(Phase 3 산출물)가 설계의 일부다.
      - `@RetryableTopic` 지연 재시도 토픽 체인을 기각한 이유(토픽 3~4개 증가 대비 이득)도 한 줄.
      - `DefaultErrorHandler`가 블로킹 재시도라 백오프를 늘리면 파티션이 정체된다는 점도.

   ⑥ **source of truth는 DB, Kafka는 fast path.** Kafka publish도 유실될 수 있으므로
      (브로커 장애/JVM 사망), tx1에서 **이미 커밋된** `payment.status=IN_PROGRESS` 행이 최후의
      방어선이다. 이미 커밋된 행은 DB 장애에도 살아남는다 — 장애 중에 새로 써야 하는 Outbox
      레코드와 결정적으로 다른 점. 다만 그 행만으로는 PG 승인 여부를 알 수 없어 PG 재조회가 필요하고,
      반대로 Kafka 메시지는 "PG 승인 성공"이라는 **DB 어디에도 없는 정보**를 담는다.
      - **정산 스윕 잡은 이번 범위 밖(다음 트랙)이지만 설계상 필요하다**는 것을 명시할 것.

   ⑦ **설계 세부와 트레이드오프**: 토픽/파티션 키(`paymentId`)/payload 최소화/`acks=all`/
      DLT 파티션 수를 원본과 맞춘 이유(`DeadLetterPublishingRecoverer`가 같은 파티션 번호로 전송)/
      `send()`를 비동기 콜백으로 처리하고 블로킹하지 않은 이유.
      (`00_overview.md` Phase 0 표를 가져와도 됨)

   ⑧ **멱등성이 왜 필수인지**: Kafka at-least-once + **DLQ 재투입**. 재투입이 중복을 만들 수 있으므로
      멱등성은 선택이 아니다.

   ⑨ **범위 밖으로 둔 것과 이유**: DLQ 자동 재처리 루프(DB가 아직 죽은 상태에서 자동 재투입하면
      무한 왕복), 정산 스윕 구현, 운영 알림 연동.

2. 이 전환 중 발견했지만 범위 밖으로 미뤄둔 것들을 **다음 트랙 메모**로 따로 남긴다:
   - Phase 4에서 삭제한 `createReservation_PaymentSuccess_DBFail_OutboxCreated`의 실패 원인 미규명.
   - `payment.status=IN_PROGRESS` 정산 스윕 잡 미구현.
   - `@EnableScheduling` 누락 — 다른 `@Scheduled`가 추가될 때 같은 함정에 빠지지 않도록 기록.
   - 그 외 작업 중 발견한 기존 결함.
